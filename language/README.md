# Language (R2)

- **5.5:** `make_grammar.py` builds `command.gbnf` from `$defs/Command` in the frozen `integration/schemas.json` (current version 1.2.0, see `docs/schemas.md`; the results below were measured on v1.0.0). Regenerate with `python3 language/make_grammar.py`. The grammar enforces integer ranges and the `place` / `event_id` patterns, but not lat/lon bounds (jsonschema checks those). Result on the frozen schema: Llama 3.2 3B Instruct Q4_K_M via llama.cpp 0.8.0 (brew, Metal with the workaround below) gave schema-valid JSON on 40/40 seeds (`language/results_5_5.csv`; temperature 0, one run, `python3 language/run_llm.py --seeds`), median latency 4.1 s (re-run on the seeds re-based to Baylands coordinates; the first run on UCSD coordinates gave 3.4 s). The action matched the seed on 35/40, informational only, and the same five seeds missed both times. This is a format check, not accuracy.
- **5.6:** `data/seeds.jsonl` holds 57 seed commands (45 valid, 12 `clarify`) for schema v1.2.0; the first 40 were written for v1.0.0, S41 to S57 cover `move`, `climb` and `descend`. Every seed is checked against the schema by `language/test_language.py`.

Run the tests: `cd language && python3 -m pytest -q` (needs `pytest` and `jsonschema`). The 57 grammar-acceptance tests are skipped unless llama.cpp's `llama-gbnf-validator` is on PATH.

Run the model: `GGML_METAL_BF16_DISABLE=1 llama-server -m ~/models/Llama-3.2-3B-Instruct-Q4_K_M.gguf --port 8080 -c 4096`.

Metal note (M2, macOS 15.6, llama.cpp 0.8.0 from brew): without the variable, the Metal shader build fails (`constexpr` error in the `unary` kernel) and the server cannot start on the GPU. Setting `GGML_METAL_BF16_DISABLE=1` lets it start with no Metal errors, and a short `hold` request ran at about 34 tokens/s generation, against about 4 on CPU (`--device none`). We did not find out why the fix works, and the server log has no Metal lines, so GPU use is inferred from speed. Over the 40 seeds the median latency stayed about 6 s (CPU 6.4 s, GPU 6.0 s). The laptop was swapping heavily (16 GB), so treat all latency numbers as a worst case.

## Dataset, guard and eval (tasks 6.4 and 6.5, in progress)

- **Dataset:** `data/dataset_batch1.jsonl` and `dataset_batch2.jsonl` (114 commands, our own wording, answer key hand-checked). `python3 language/split_dataset.py <batch>` adds a batch to `data/train.jsonl` (tune on this) and `data/test.jsonl` (held out, about 20%, split per tag). Existing rows never move. The test file is scored once at the end; do not tune on it.
- **`guard.py`:** `normalize_units` turns number words, feet, kilometers and minutes into digits, meters and seconds before the model. `check_grounding` turns a command into `clarify` when a value is not in the operator's words (stops invented altitudes, coordinates and event ids). It does not check climb versus descend direction.
- **`eval.py`:** `python3 language/eval.py` scores the train split, model alone and after the guard. `--split test --final` scores the held-out set, prints totals only and logs the run to `test_runs.log`. Needs `llama-server` running.
- **Baseline on the train split** (91 rows, one run, temperature 0, our own synthetic data, simulator project): action accuracy 78%; exact 58% model alone and 65% after the guard; wrong commands that would fly 30 before the guard and 3 after (all climb/descend direction swaps). Biggest failure: place names (1 of 15 place-based rows exact). The places table does not exist yet; the place names in the dataset are placeholders.
- Run the tests: `cd language && python3 -m pytest -q`.
