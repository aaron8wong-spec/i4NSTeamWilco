The challenge (from the sponsor sheet) Title: Army-737 "Say Less, Fly More." Run through DIU's Innovation with Academia (IWA). Sponsor: U.S. Army. Problem: Dismounted drone operators need to manage unmanned systems with intent-based natural-language control, because manual interfaces cause extreme cognitive overload during combat operations. Key points from the sheet: Operators already carry a full combat load, and a control interface full of buttons and knobs is not sustainable. Current voice systems use rigid, scripted phrases. They break when conditions change. An agentic AI should understand high-level intent: the operator describes what they need and the system works out how. It must run locally, with no cloud and no external power, on low-power, portable edge hardware. The edge hardware market is dominated by proprietary architectures (Nvidia). Finding alternative chips with lower power use is an open problem. A closed-loop feedback mechanism is needed: the local model looks at imagery, tells the operator what it detects (terrain changes, anomalies), and takes follow-up natural-language commands without a mode switch. Suggested starting point for an academic team: evaluate alternative edge hardware and tune a lightweight model for basic intent tracking, rather than attempting full system integration from the start. Beneficiaries: airborne infantry squads, special operations teams, small-unit reconnaissance, robotic and autonomous systems program offices.
Our concept (in one paragraph) Three parts: the drone, a local compute node, and the operator. The operator speaks a task, and the drone flies it and tells the operator only what matters. It works like a DJI Mavic: manual flight is always available, and AI mode is a separate switch. The AI narrates on request, not continuously. One request can imply a long multi-step task, for example: "Go over the ridge and search for vehicles; if you see some, identify the type and any people inside." Open questions we are researching through interviews: How does the system behave under jamming or degraded comms, and what should the drone do when it loses contact mid-task? How much autonomy will operators trust for long tasks? What reporting helps an operator under stress, and what is noise? What latency and hardware budget does on-device speech and language processing allow? Interview findings so far point to small on-device models, lower-power compute options, and the fact that voice adds failure modes (noise, stress, misrecognition).
The MVP we are building (weeks 5-9) Two goals, one loop: Deterministic flight from voice commands. The operator's words become a structured command, pass a safety gate, and move a simulated drone predictably. Report only what matters. As the simulated drone flies, events come back. Code decides which ones to interrupt the operator about, which to summarize, which to log, and when to ask first. What links them is the mission. A command like "search the north field for vehicles" sets a target in mission_state. That target drives both the flight (a search pattern) and the scoring (what counts as relevant). An alert can ask a question, and the operator's answer re-enters through the same command path. One demo scenario (everything is built to serve this): Operator: "Search the north field for vehicles." Drone flies the search pattern in the simulator. Planted events fire as the drone nears them: a deer, a truck, a truck with two people, a low-confidence blob. Scorer: deer → log; truck → summarize; truck with people → interrupt; low-confidence risky object → ask first. Drone says: "Vehicle with two people at the east edge. Loiter?" Operator: "Yes, loiter." The drone loiters. Core design rule: the LLM suggests, deterministic code decides. The language model only turns text into one of a fixed set of JSON commands. A safety gate in plain code checks every command. The language model never talks to the autopilot directly. Architecture: COMMAND PATH: voice -> whisper.cpp -> text (+ mission_state) -> llama.cpp + GBNF grammar -> JSON command -> safety gate -> MAVSDK -> PX4 SITL + Gazebo -> drone moves

REPORT PATH: sim emits scripted events (with noisy confidence) -> rules lookup -> scorer -> tier (interrupt / summarize / log / ask) -> templated message -> operator (text on screen; speech is a stretch)

SHARED: schemas, mission_state, eval harness, hardware benchmarks

When the REPORT PATH asks a question ("Loiter?"), the operator's answer re-enters the COMMAND PATH, with mission_state.pending_question passed to the model so "yes" means something.

How event planting works (what is real and what is faked: the drone's "vision" is faked, everything else is real): A scenario file lists the planted finds as meters north and east of home: id, type, people_visible, confidence. A Python loop reads the drone's position from MAVSDK, converts it to meters from home, and fires each find once when the drone gets within about 60 m. The 60 m stands in for camera range. A small random amount is added to the confidence. Gazebo truck and person models are optional and only for looks. Events never come from Gazebo. Two gotchas: read the home position from the sim instead of hardcoding it, and convert lat/lon to meters correctly.

Scope: what we build, and what we do NOT build In scope (must have): Typed text -> JSON -> safe simulated flight, with the safety gate enforced. Command dataset and measured accuracy on a held-out test set. Scripted event feed, rules table and scorer, with measured precision and recall. Ask-first loop. Should have: live whisper.cpp voice input; one multi-step command; a hardware benchmark table. Stretch: LoRA fine-tune (only if accuracy is clearly low); spoken output; lost-link demo polish; power measurements. Out of scope. Plan only, in the roadmap: real camera perception, real drone hardware, jamming tests, alternative-chip deep dive, ROS 2 / Micro-XRCE-DDS, cloud services (Pinecone etc.), a vector database (ChromaDB is a stretch, not a requirement). Honest limits we must state in every presentation: Perception is simulated. Events are scripted, not detected by vision. Results are from a simulator, not real flights. Accuracy numbers come from our own synthetic data.
Schemas (FROZEN v1.2.0) Source of truth: integration/schemas.json (JSON Schema). Explanation and examples: docs/schemas.md. Both were frozen after the team vote. Any change needs a team vote, a version bump, a grammar rebuild (python3 language/make_grammar.py), updated seeds and a re-run of the accuracy eval. If this section and schemas.json disagree, schemas.json wins; fix this section. Units: meters, seconds, WGS84 lat/lon. Altitude is meters above home. Names carry the unit: alt_m, radius_m, duration_s, time_s. Distances and times in commands are whole numbers. Command (the only things the language model may output). One JSON object, "action" first, then "params". Ten actions: {"action": "goto", "params": {"place": "north_field", "alt_m": 40}} {"action": "search_area", "params": {"place": "north_field", "radius_m": 150, "alt_m": 50, "target": "vehicle"}} {"action": "loiter", "params": {"event_id": "E03", "radius_m": 30, "duration_s": 120}} {"action": "move", "params": {"distance_m": 500, "bearing_deg": 45, "alt_m": 40}} {"action": "climb", "params": {"amount_m": 61}} {"action": "descend", "params": {"amount_m": 20}} {"action": "hold", "params": {}} {"action": "return_home", "params": {}} {"action": "report_status", "params": {}} {"action": "clarify", "params": {"reason": "missing_altitude", "question": "How high should I fly?"}}

Location in goto, search_area and loiter is given one way, never mixed: a place name, or lat plus lon, or (loiter only) an event_id. The model should prefer place and use lat/lon only when the operator states coordinates. search_area target is one of vehicle, person, structure, any. loiter has no altitude (it keeps the current one). move goes distance_m from the drone's current position on bearing_deg (whole degrees clockwise from true north, 0 to 359) at alt_m, which is required. Compass words ("northeast") are not accepted: the model uses clarify. climb and descend change height by amount_m from the current altitude, over the same spot (two actions, because the grammar cannot write negative numbers). report_status reads out what was found since the last report (the summarize list). clarify reason is one of missing_location, missing_altitude, ambiguous_reference, unsupported_action, unsafe_request, unclear_speech. Use clarify for vague, impossible or unsafe requests. Do not guess a value. Ranges in the schema are outer bounds so the grammar can keep the model inside them. They are not safety limits. The safety gate applies the real limits and refuses with a reason (alt_m 800 is valid JSON the gate can refuse). Not in v1.2.0 (adding any is a schema change): multi-step commands (a list of commands), compass-word moves ("10 m north"), setting an absolute altitude without a place, "follow me", and anything involving weapons or engagement. Places: a place name must be resolved to lat/lon by code from a places table. A name not in the table is refused with a reason (it is not a model failure). The table does not exist yet (integration/places.json). Build it from the Gazebo Baylands world. The world file baylands.sdf places 3D visual models (building_1, bridge, ground_plane, trees) at local (X, Y, Z) meter coordinates and has one GPS origin anchor, 37.412173, -121.998878. Convert each chosen local point to lat/lon with flight/geo.py (not built yet): north_m is Y and east_m is X if the world is ENU, which must be checked in the SDF and in Gazebo before trusting it. The origin must match PX4's home (the sim prints "[SIM] home ..."). Place names are points we choose, not model names; pick open ground near visible landmarks and check each one in the Gazebo view. The place names in data/ are placeholders until this table exists. Owner to be decided. Event (what the simulated drone "sees"): {"id": "E03", "type": "vehicle", "confidence": 0.79, "lat": 32.8821, "lon": -117.2384, "time_s": 142.5, "people_visible": 2, "subtype": "truck"}

type is one of vehicle, person, structure, wildlife, unknown. subtype is optional (up to 32 characters). Ids look like E03. mission_state (one shared copy, owned by mission_state.py; other modules read it and keep no copies of their own): { "target": "vehicle", "area": {"lat": 32.8815, "lon": -117.2380, "radius_m": 150, "alt_m": 50}, "geofence": {"lat": 32.8800, "lon": -117.2400, "radius_m": 500, "max_alt_m": 120}, "home": {"lat": 32.8800, "lon": -117.2400}, "already_reported": ["E01"], "pending_question": {"text": "Vehicle, 2 people nearby (rule R03: vehicle with people is high priority). Loiter there?", "event_id": "E03", "proposed_command": {"action": "loiter", "params": {"event_id": "E03", "radius_m": 30, "duration_s": 120}}}, "mode": "ai" }

target, area, home and pending_question can be null. The geofence values are an example, not our limits; they come from config. home is read from the sim. Rule (one entry in rules.json, which is {"rules": [ ... ]}): {"id": "R03", "event_type": "vehicle", "condition": {"people_visible_min": 1}, "priority": "high", "min_confidence": 0.6, "action": "interrupt", "reason": "vehicle with people is high priority", "safety_relevant": true}

event_type is an event type or "any". condition keys are optional (people_visible_min, in_search_area, matches_target); all listed keys must hold and {} always holds. action is a tier: interrupt, summarize, log or ask. reason is up to 200 characters. OperatorMessage (what the scorer produces for the operator): {"tier": "ask", "event_id": "E03", "rule_id": "R03", "text": "Vehicle, 2 people nearby (rule R03: vehicle with people is high priority). Loiter there?", "expects_reply": true}

Scoring logic (version 0, plain code) For each event, in this order: If event.id is already in already_reported, or it is a near-duplicate of one, tier = log. Find rules matching event.type (or "any") and the condition. Take the highest priority. If the type does not match mission_state.target and the rule is not safety_relevant, tier = log. If priority is high and event.confidence < rule.min_confidence, tier = ask, and set pending_question. Otherwise: high priority -> interrupt; medium -> summarize; low -> log. Summarized events wait until the operator asks (report_status). Still to be written down by R4 in the scoring spec: what happens when an event matches a rule but is below min_confidence and the priority is not high, and which rule wins when several match with the same priority. The message is a template that includes the rule's reason, so every alert can say why. The LLM may be used later to reword messages. It does not make the decision.
Safety gate (every command must pass) Geofence (stay inside the radius from home). Maximum altitude. Minimum battery to continue (below it, force return home). Lost-link behavior: hold, then return home. Manual override: if mode is manual, AI commands are ignored. Anything outside the schema or outside limits is refused, not "fixed." That includes a place name that is not in the places table.

How to describe it to different audiences Engineers / technical judges: grammar-constrained decoding gives valid JSON every time; a deterministic state machine gates every command; MAVSDK talks to PX4 SITL; rules are retrieved and scored in code; results are measured on held-out data. Program officers / sponsor: an operator cannot fly a controller and watch their surroundings. They give one spoken task and the drone only interrupts when it matters. It runs offline. The roadmap covers real perception, real hardware, jamming tests and alternative low-power chips. Operators / interviewees: show the scenario video and ask what they would want to be interrupted about. Their answers change the rules table. One-sentence version: "Tell the drone what to do, and it only interrupts you when it matters."
